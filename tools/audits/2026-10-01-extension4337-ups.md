## 1. How the system actually enforces authority (the one thing the whole audit turns on)

A user operation carries `callData` that the **EntryPoint executes against the UP** (`EntryPoint.sol:246`, `Exec.call(sender, 0, callData, callGasLimit)`). There are two independent permission checks, on two different principals:

**(A) Validation — checks the SIGNER.** EntryPoint → `UP.validateUserOp` → (no native fn) LSP17 fallback → `Extension4337.validateUserOp` (`01-.../Extension4337.sol:65`). The extension:
1. requires its appended caller to be the EntryPoint — `require(_extendableMsgSender() == _ENTRY_POINT)` (`:71`);
2. recovers the signer from `personal_sign(userOpHash)` (`:77-78`);
3. requires the signer to hold `_4337_PERMISSION` = `0x800000`, else returns `1` (SIG_VALIDATION_FAILED) (`:81-88`);
4. calls `KeyManager.lsp20VerifyCall(requestor=EP, target=UP, caller=signer, value=0, callData)` (`:94-100`). Because the caller here is the **extension, not the UP**, the KM takes its read-only branch (`LSP6KeyManagerCore.sol:359-377`) and runs `_verifyPermissions(UP, signer, false, callData)` — i.e. it checks **the signer's own permissions and AllowedCalls** against the exact `callData`.
5. If the returned selector isn't the success value, returns `1` (`:103-108`); else `0`.

**(B) Execution — checks the ENTRYPOINT.** EntryPoint calls the UP with the same `callData`, `msg.sender = EntryPoint`. Every state-changing UP entrypoint (`execute`, `setData`, `transferOwnership`, …) sees `msg.sender != owner` and routes to `LSP20._verifyCall(owner)` → `KM.lsp20VerifyCall` with `msg.sender = UP = target`, so the KM takes its **owner branch** (`LSP6KeyManagerCore.sol:340-356`) and runs `_verifyPermissions(UP, caller=EntryPoint, …)` — i.e. it checks **the EntryPoint's own permissions**, which on all three UPs are exactly `0x500 = SUPER_CALL | SUPER_TRANSFERVALUE` and nothing else.

So an operation only takes effect if **both** the signer (at validation) **and** the EntryPoint's `0x500` (at execution) permit the exact same bytes. The `callData` is identical in both phases, so there is no "validate one thing, execute another" gap (section 6 tests this). This two-principal split is the backbone of every verdict below.

One more fact that matters everywhere: **when only the *execution* reverts, `handleOps` does not revert** — `innerHandleOp` catches it, emits `UserOperationRevertReason`, and the paymaster still pays (`EntryPoint.sol:246-253`). The relayer compensates by simulating the execution alone before sending (`relay.js:240`), but the EntryPoint itself will still charge a paymaster for an op that passes validation and reverts at execution.

## 4. Threat model recap

- **Users:** a few known UPs (yours + partners). **Attacker classes considered:** (a) an outsider with no key; (b) a holder of a controller **without** the 4337 bit; (c) a holder of a 4337 key with **minimal** permissions (e.g. CALL + one AllowedCall); (d) a malicious/compromised holder of a **full** 4337 controller (`0xff3f06`); (e) a malicious **relayer**; (f) a malicious **allow-listed partner UP**. The paymaster owner ("cassa") and the KM-owner EOA are trusted.

## 5. Property verdicts P1–P5

Legend: **[verified-src]** = proven from the cited source; **[verified-lab]** = reproduced on the local chain (both 0.14.0 and 0.12.1), test IDs in brackets.

### P1 — Only a 4337-holder gets an op validated, and only for what its OWN permissions/AllowedCalls allow. **HOLDS.**

- The signer-check is the *only* place the signer is authenticated: `Extension4337.sol:81-88` (must hold `0x800000`) then `:94-100` → KM read-only `_verifyPermissions(UP, signer, …)` (`LSP6KeyManagerCore.sol:359-377, 532-639`). **[verified-src]**
- A key without the 4337 bit cannot validate anything, even with CALL+VALUE+SUPER perms — returns `1` ⇒ EntryPoint `AA24` (`EntryPoint.sol:469`). **[verified-lab P1e]**
- A 4337 key with **CALL but no TRANSFERVALUE** cannot move value: `_verifyCanCall` requires TRANSFERVALUE (`LSP6ExecuteModule.sol:200-206`) ⇒ `AA24`. **[verified-lab P1b]** (matches your ganache result.)
- A minimal 4337 key with an AllowedCall to one target **cannot** call elsewhere, **despite the EntryPoint holding SUPER_CALL** — the restriction is applied to the signer at validation (`_verifyAllowedCall`, `LSP6ExecuteModule.sol:237-292`, `NotAllowedCall`): call to a non-allowed target ⇒ `AA24`; call to the allowed target succeeds. **[verified-lab P1c/P1d]**
- Happy path: a sponsored `execute(CALL)` value transfer validates, executes, moves funds, controller spends no gas. **[verified-lab P1a]**

Caveat H-1: on the three real UPs the controller has SUPER_CALL | SUPER_TRANSFERVALUE and empty AllowedCalls, so for *that* key P1's "only what its AllowedCalls allow" is vacuous — it may call anything and move any value/token. That's the intended owner-level key; see H-1.

### P2 — Nothing through the EntryPoint can change UP data, permissions, extensions or owner. **HOLDS** (on exactly one invariant — M-2).

Execution authority = EntryPoint's `0x500` = SUPER_CALL | SUPER_TRANSFERVALUE only. That word cannot express SETDATA, ADD/EDIT-controller, CHANGEOWNER, ADD/CHANGE-extension, or DELEGATECALL. Concretely:

- **Direct `setData`/`setDataBatch` op:** passes validation (controller has SUPER_SETDATA) but at execution the KM checks the EntryPoint ⇒ `NotAuthorised(EntryPoint,"SETDATA")`; data unchanged. **[verified-lab P2a]**
- **Permission self-escalation `setData(permKey, …|CHANGEOWNER)`:** same — reverts at execution, controller perms unchanged. **[verified-lab P2b]**
- **`execute(CALL, to=UP, setData(...))` (self-call):** nested call re-enters the UP with `msg.sender = UP`, which has no controller permissions ⇒ `NoPermissionsSet`/reentrancy revert; data unchanged. **[verified-lab P2c]**
- **`execute(CALL, to=KeyManager, …)`:** rejected at validation — `LSP6ExecuteModule.sol:67-69` `revert CallingKeyManagerNotAllowed()`. **[verified-lab P2d]**
- **`transferOwnership` op:** this controller lacks CHANGEOWNER ⇒ rejected at validation (`LSP6OwnershipModule.sol:14-29`). Even a signer *with* CHANGEOWNER is stopped at execution because the EntryPoint lacks CHANGEOWNER — no pending owner set. **[verified-lab P2e/P2f]**
- **`batchCalls([...])` (LSP0's self-`delegatecall`):** `batchCalls` is not among the selectors `_verifyPermissions` recognises ⇒ `revert InvalidERC725Function` at validation; perms unchanged. (Even if it reached execution, the inner `setData` runs with `msg.sender = EntryPoint`, lacking SETDATA.) **[verified-lab E1]**
- **DELEGATECALL op:** `LSP6ExecuteModule.sol:133-135` `DelegateCallDisallowedViaKeyManager` — unconditional. **[verified-src]**

**M-2:** P2 holds solely because the EntryPoint controller's word is `0x500`. There is no second barrier: if the EntryPoint were ever granted SETDATA (bad setup, a future change to `EP_PERMS`, or a hand-rolled batch), permission/data changes *would* flow through the relayer. The page hard-codes `EP_PERMS = SUPER_CALL | SUPER_TRANSFERVALUE` (`up-gas-relay.html:260`) and the post-setup check asserts `ep == 0x500`, which is good, but it's one line between "safe" and "relayer can rewrite the UP." Treat `AddressPermissions:Permissions:<EntryPoint> == 0x0000…0500` as a monitored invariant on every UP, on every chain.

### P3 — No replay across chains, UPs or nonces. **HOLDS.** **[verified-src + lab]**

`userOpHash = keccak256(hash(userOp), entryPoint, chainId)` (`EntryPoint.sol:267-269`) and `hash(userOp)` includes `sender` and `nonce`. The extension recovers from `personal_sign(userOpHash)`, so the signature is bound to (UP, nonce, EntryPoint, chainId).

- Cross-chain: a signature made for another chainId recovers a different address ⇒ no 4337 bit ⇒ `AA24`. **[verified-lab P3a]** (The same UP address + same controller on Base/Polygon is safe precisely because chainId is in the hash.)
- Cross-UP: a signature for UP-A fails on UP-B (different `sender` ⇒ different hash). **[verified-lab P3b]**
- Nonce: `NonceManager._validateAndUpdateNonce` consumes each (sender,key,seq) once; a resubmitted op ⇒ `AA25`. **[verified-lab P3c]**

### P4 — Paymaster pays only for allow-listed UPs within cap; only the owner moves the deposit; the relayer can't steal/redirect. **HOLDS** (see M-1 for the griefing nuance).

- `validatePaymasterUserOp` (`UPPaymaster.sol:45-53`): `require(msg.sender == entryPoint)`; `if (!sponsored[sender] || maxCost > maxCostPerOp) return ("",1)`; reads only `sponsored[sender]` (sender-keyed, ERC-7562-clean for an unstaked paymaster). Non-allow-listed ⇒ `AA34`; over-cap ⇒ `AA34`. **[verified-lab P4a/P4b]** Cap starts at 0 ⇒ nothing sponsored until the owner sets it. **[verified-src]**
- Deposit: `withdrawTo`/`setSponsored`/`setMaxCostPerOp` are `onlyOwner`; funding is a plain `receive()` → `entryPoint.depositTo` (`:61-81`); two-step ownership (`:84-94`). Non-owner withdraw reverts `NotOwner`; owner withdraw allowed. **[verified-lab P4c]**
- Relayer can't redirect funds: the `to`/`value` live inside the signed `callData`; altering them breaks the signature. The relayer choosing itself as `beneficiary` is just the legitimate gas reimbursement. The relayer EOA `0xbb6839…63C2F` holds no permission on any UP (confirmed by the reports). **[verified-src]**
- Reaching the paymaster through an op (`execute(CALL, to=PM, withdrawTo/…)`) fails: the caller is the UP, not the cassa ⇒ `NotOwner`. Reaching the EntryPoint (`withdrawTo`) withdraws from the *UP's* own (zero) deposit, never the paymaster's (deposits are address-keyed; `StakeManager.sol:116-122`). `handleOps` re-entry hits `nonReentrant`. **[verified-src]**

### P5 — The revoke batch fully restores the pre-setup state. **HOLDS.** **[verified-lab]**

On a pristine UP, running `buildSetup` (`up-gas-relay.html:1096`) then `buildRevoke` (`:1161`) returns **every** touched data key — controller permissions, the `LSP17Extension:0x3a871cdd` key, the EntryPoint's permission word, and `AddressPermissions[]` length — to its exact pre-setup bytes, and afterwards no op can be validated. **[verified-lab P5 isolated: pre == post on both versions]** Revoke removes the EntryPoint array entry by moving the last element into its slot and shrinking the array; on the three real UPs the EntryPoint is the last entry (index 2), so that path is a plain truncate. The temporary CHANGEEXTENSIONS grant used to clear the extension key is removed in the same atomic `executeBatch`.

## 6. Privilege escalation — enumerated and attacked

For every path requested in the brief, the result and the exact blocking check. "signer-restricted" = bounded by the signer's own perms at validation; "EP-restricted" = bounded by the EntryPoint's `0x500` at execution. Unless noted, a blocked execution still lets the EntryPoint charge the paymaster (M-1).

| # | Path through the EntryPoint | Signer = full `0xff3f06` controller | Signer = minimal 4337 key | Blocked by |
|---|---|---|---|---|
| 1 | `execute(CALL, any, value, data)` | **possible** (intended) | only if signer's AllowedCalls/TRANSFERVALUE permit | validation: `_verifyCanCall`/`_verifyAllowedCall` `LSP6ExecuteModule.sol:182-292`; execution: EP SUPER_CALL/VALUE |
| 2 | `setData`/`setDataBatch` (perms, URD, extension, any key) | validates, **reverts at execution** | rejected at validation (no SUPER_SETDATA) | exec: EP has no SETDATA → `NotAuthorised` **[P2a/P2b]** |
| 3 | `execute(CALL, to=UP, setData/execute)` self-call | validates, **nested revert** | blocked at validation unless UP in AllowedCalls | `NoPermissionsSet(UP)`/reentrancy **[P2c]** |
| 4 | `execute(CALL, to=KeyManager, …)` | **rejected at validation** | rejected at validation | `CallingKeyManagerNotAllowed` `LSP6ExecuteModule.sol:67-69` **[P2d]** |
| 5 | `transferOwnership` / `renounceOwnership` / `acceptOwnership` | rejected at validation (no CHANGEOWNER); and EP-blocked even with it | rejected at validation | `LSP6OwnershipModule.sol:14-29` + EP `0x500` **[P2e/P2f]** |
| 6 | `batchCalls([...])` (LSP0 self-delegatecall) | **rejected at validation** | rejected at validation | `InvalidERC725Function` `LSP6KeyManagerCore.sol:637` **[E1]** |
| 7 | DELEGATECALL via `execute(4,…)` | rejected at validation | rejected at validation | `DelegateCallDisallowedViaKeyManager` `LSP6ExecuteModule.sol:133-135` |
| 8 | `execute(CALL, to=EntryPoint, withdrawTo/addStake/depositTo)` | executes, but touches only the **UP's own** (zero) deposit; `handleOps` re-entry hits `nonReentrant` | signer-restricted | `StakeManager.sol:116`; `EntryPoint.sol:92 nonReentrant` |
| 9 | `execute(CALL, to=Paymaster, setSponsored/withdrawTo/…)` | executes, **reverts** (caller≠owner) | signer-restricted | `UPPaymaster.sol:31-33 onlyOwner` |
| 10 | `execute(CALL, to=other controller/URD)` to make *it* act | signer-restricted; URD's `universalReceiverDelegate` only writes LSP5/LSP10 keys via `setDataBatch` **called back on the UP**, which then needs the caller's SETDATA — the URD has it, but the URD is only invoked on token hooks, not reachable to escalate UP perms | same | KM re-checks on the callback; EP path can't set perms |
| 11 | LSP17 fallback to another extension | only `validateUserOp`→Extension4337 is registered; calling it not-from-EntryPoint reverts `"Only EntryPoint…"`; it is read-only regardless | same | `Extension4337.sol:71`; **[E2/E3]** |
| 12 | SUPER_TRANSFERVALUE to move value/tokens beyond signer's TRANSFERVALUE/AllowedCalls | the callData is identical at validation and execution, so the EP's SUPER can't widen the signed `to`/`value`; a signer without TRANSFERVALUE is stopped at validation | same | `LSP6ExecuteModule.sol:200-206`; **[P1b]** |
| 13 | callData that `lsp20VerifyCall` accepts but executes differently (value field, op type, nested batch, abi tricks) | none found — same bytes decoded the same way in both phases; `execute` value is checked at validation against the embedded value, not the extension's `value:0` (I-1) | same | `LSP6KeyManagerCore.sol:579-595` |
| 14 | Replay on another UP / chain / nonce / EntryPoint | blocked — hash binds all four | blocked | `EntryPoint.sol:267-269`; **[P3a/b/c]** |

**Controllers without the 4337 bit** (e.g. the URD, `0x060080`): cannot initiate any op (`Extension4337.sol:81-88`), and cannot be *passively* altered by an op, because altering their permissions needs SETDATA which the EntryPoint lacks (path 2). So the URD's REENTRANCY + SUPER_SETDATA (reports' "[0] has REENTRANCY", L-2) is **not reachable** through the 4337 flow; it only matters inside the normal token-hook reentrancy the KM already governs.

**Net:** no path produces more authority than the signer already holds. The one honest escalation is **H-1**: gas abstraction makes a *compromised controller key* exploitable **without the attacker holding any gas** and via a **MetaMask-producible** `personal_sign` (LSP25 relay calls need an EIP-191 v0 sig MetaMask won't make). It grants nothing the key couldn't already do by paying gas / signing a relay call — but it lowers the bar and removes the "attacker needs to fund the key first" friction. The mitigation is key hygiene and small balances, not code.

**M-1 (paymaster griefing), step by step:** (1) a UP is allow-listed (yours or a partner's) and holds a 4337 controller; (2) that controller signs an op that passes validation but reverts at execution — e.g. a `setData` op (path 2), or any `execute` to a target that reverts; (3) it is submitted **directly to the EntryPoint** by *any* address (your own `relay.js` refuses it at `relay.js:240`, but a third party need not use your relayer); (4) `innerHandleOp` runs it, execution reverts, but the paymaster is still charged `actualGasCost` up to `maxCostPerOp` (`EntryPoint.sol:246-253, 556-593`); (5) repeat until the deposit is drained. **Bound:** `maxCostPerOp` per op × deposit size, and only from allow-listed UPs. **Fixes:** keep deposits small (already your stated practice); only allow-list UPs you trust not to grief (partners are a trust decision, not a code guarantee); optionally add a per-sender spend/throttle in `postOp` + a small stake so the paymaster can use reputation; consider removing a UP from the allow-list the moment it misbehaves.

## 7. Fixes (consolidated)

- **M-2:** monitor, on every UP and chain, the invariants `perms[EntryPoint] == 0x500`, `perms[controller] & 0x800000 != 0` with no SETDATA/CHANGEOWNER/ADD-EDIT beyond intent, and `LSP17Extension:0x3a871cdd == Extension4337`. The page already asserts these post-setup; add an off-chain watcher that re-checks periodically and on each new chain. Never let a batch grant the EntryPoint SETDATA.
- **M-1 / L-1:** keep paymaster deposits small (done); allow-list only trusted UPs; consider a staked paymaster with `postOp` throttling/accounting if partner UPs are ever allow-listed at scale.
- **L-3:** keep the relayer's `preVerificationGas` check but also **cap the upper side** (reject ops whose implied `maxCost` is wildly above a sane estimate) so a mis-set `preVerificationGas` can't quietly spend the paymaster up to the per-op cap.
- **H-1:** controller-key hygiene (hardware wallet / separate 4337 key with *minimal* AllowedCalls if a UP only ever needs to call known targets); keep only small amounts on UPs that carry a gasless 4337 controller.
- **I-3:** before trusting Extension4337 in production value flows, keep pressing LUKSO for its audit status; it has (almost certainly) never run on LUKSO mainnet (no EntryPoint there). Nothing in the integration itself is unsafe as reviewed, but the extension's own code is unaudited upstream.
